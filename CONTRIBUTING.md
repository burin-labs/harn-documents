# Contributing to harn-documents

This is a published Harn package. Consumers install a tagged version with
`harn add github.com/burin-labs/harn-documents@vX.Y.Z` and import the functions
that `harn.toml` exports. That makes the export surface a contract: once a
function is released, changing its shape breaks installs that already pin it.
Everything below follows from that.

## What belongs in this package

The package owns document-domain behavior and nothing else:

- The report shape, and normalizing a loose dictionary into it.
- Rendering that shape to Markdown and to Typst.
- Building argument lists for an external renderer.
- Portable file and manifest specs describing a document artifact.

Harn owns the rest of the pipeline: validating artifact specs, recording them
into a session, and projecting the resulting events to agent protocols. The
package deliberately does not run processes. `typst_compile_command` returns the
argument list and stops, so the calling harness keeps control of command policy,
execution, and verification.

Use that split to place a change. If your change decides *what a document looks
like*, it belongs here. If it decides *what happens to a document once it
exists*, it belongs in [`burin-labs/harn`](https://github.com/burin-labs/harn).
A change that adds process execution to this package is in the wrong repository
no matter how convenient it is.

## Setting up

Install the toolchain version pinned in `.harn-version`:

```bash
cargo install harn-cli
harn --version
```

## Verifying a change

Run the same checks CI runs. They are the authoritative gate, and they are fast
enough that there is no reason to push without them:

```bash
harn check --strict-types lib.harn main.harn tests/test_main.harn
harn fmt --check lib.harn main.harn tests/test_main.harn
harn lint --strict lib.harn main.harn tests/test_main.harn
harn test tests/ --parallel
harn package check
harn package docs --check
harn package pack --dry-run
```

Two of those catch mistakes that are easy to miss:

- `harn package docs --check` fails when `docs/api.md` no longer matches the
  code. That file is generated by `harn package docs`, so regenerate it rather
  than editing it by hand.
- `harn package pack --dry-run` fails when the package would not install
  cleanly for a consumer, which a passing test suite will not tell you.

Renderers stay deterministic on purpose. Given the same report,
`render_markdown_report` and `render_typst_report` must produce byte-identical
output every time, because consumers diff and hash the results. If your change
introduces a timestamp, a map iteration order, or anything else that varies
between runs, it is a defect even when the tests pass.

## Changing the export surface

The functions listed under `[exports]` in `harn.toml` are what consumers import.
When you change them:

1. Add or update a test in `tests/test_main.harn` first, so the new behavior has
   a falsifier before it has an implementation.
2. Regenerate the reference with `harn package docs`.
3. Add a line to the `## Unreleased` section of `CHANGELOG.md` describing the
   change in terms of what a consumer sees, not which files moved.
4. Follow SemVer. A new function is a minor bump. Renaming, removing, or
   changing the arguments of an existing exported function is a breaking change,
   and it needs a decision before you write it, because every pinned consumer
   pays for it.

The Harn compatibility range lives in `harn.toml` as `harn = ">=0.10.28,<0.11"`.
Widen or raise it only when you have actually run the suite against the version
you are claiming support for.

## Pull request titles

Title every pull request `[Area] Sentence case`. The area is one bracketed word
naming the part you touched, and the sentence that follows says what the change
does, capitalized like a sentence and with no trailing period.

```
[Rendering] Escape pipe characters in Markdown table cells
[Artifacts] Accept a checksum on a manifest entry
[Docs] Regenerate the API reference for 0.1.8
[CI] Advance the package workflow pin
```

Common areas here are `Rendering`, `Artifacts`, `Skills`, `Docs`, and `CI`.
Describe the change in three to five sentences in the body and name the command
you ran to verify it.

## Reporting a problem

Open an issue with the report dictionary you passed in, the output you got, and
the output you expected. For a rendering defect, the smallest report that
reproduces it is worth more than a description of the symptom.

Report a security problem privately rather than in a public issue.
